# Situated prompt diet

This experiment asks whether a mind needs the whole protocol on every ordinary
wake-up. The design is **Matador-derived**: keep the stable orientation and
small operating surface in the prompt, and bring exceptional detail into view
only when the body's state requires it. The source for the implementation is
the [`situate` change in this repository](https://github.com/Wouterbeets/self/blob/experiment/situated-prompt-diet/pipe.go);
this is an exploratory engineering test, not a reproduction or citation of a
Matador result.

## Hypothesis and mechanism

An ordinary situated turn should carry only the truthful finite-context frame,
the instance brief, a minimal wire contract, and the ask. The complete contract
remains available through `self help`. If a declaration is pending, the prompt
conditionally adds the details needed to author and test its command or view,
including the exact `script.authored` schema and execution boundary. Thus the
diet removes repeated instructions without hiding information needed for a
state-dependent action.

The expected benefit is less prompt surface and less repeated prose competing
with durable evidence. This fixture does **not** test whether a language model
makes better decisions, remembers more, or completes more useful work.

## Protocol

`run.sh` builds two isolated arms:

* **Control:** `CONTROL_REF` (default `4410bcd`, the last full-protocol main), which carries the full marked protocol
  section in each situated prompt.
* **Treatment:** the current worktree, which carries the diet and conditional
  pending section.

Each arm is seeded through the public `self hear` door with one
`command.declared` event. A deterministic `examples/mind-stub` reads pass 1,
authors the pending `entry` command, and emits silence on pass 2. The harness
then renders the prompt again and checks the unchanged, capability-ready state.
Homes, logs, prompt files, and mind output are separate per arm; temporary
homes are deleted unless `KEEP=1` is used.

Measured metrics are exact prompt bytes per pass, event-log growth, mind output
line count and exit status, and `hear` exit status. The pass structure tests
both the exceptional pending path and the ordinary path after authoring.

## First exploratory result

From [`result.txt`](result.txt), generated by the harness:

| arm | pending pass | ordinary pass | event lines | mind output |
|---|---:|---:|---:|---:|
| control | 6,788 bytes | 6,509 bytes | 2 | 1 then 0 lines |
| treatment | 2,527 bytes | 1,343 bytes | 2 | 1 then 0 lines |

Both arms had mind and `hear` exit status 0 on both passes. The treatment was
about 63% smaller on the pending pass and 79% smaller on the ordinary pass in
this fixture. The equal state transition is useful evidence that the fixture
still exposes the authoring contract; it is not evidence of equal model
quality. Byte counts are implementation measurements, not a universal token
saving claim.

## Reproduction

From the repository root, with Go installed:

```sh
go test ./...
go vet ./...
experiments/situated-prompt-diet/run.sh
```

To retain every artifact and inspect the exact prompt bytes without touching a
real `SELF_HOME`:

```sh
KEEP=1 experiments/situated-prompt-diet/run.sh
```

The deterministic mind can be replaced with an executable filter:

```sh
MIND=/path/to/filter experiments/situated-prompt-diet/run.sh
```

For a manual Pi/Luna exploration, build the treatment and use a fresh isolated
home. Do not commit model-generated repository changes:

```sh
go build -o /tmp/self-diet .
SELF_HOME=$(mktemp -d) /tmp/self-diet loop --max-passes 12 --timeout 30m -- \
  pi --provider github-copilot --model gpt-5.6-luna --no-session -p
```

## Caveats

This is one deterministic fixture and one exploratory implementation run. It
has no randomized assignment, repeated model trials, human utility measure,
quality rubric, tokenization control, or statistical power. Control and
treatment are source snapshots rather than two independently released builds;
`HEAD` and the current worktree can differ for reasons other than prompt size.
The stub's successful output only checks the wire and harness plumbing.

The harness also installs the experiment goal capabilities into a third isolated
home and proves structural dependency behavior: a `qa` goal depending on
`build` appears under Blocked, rejects progress while `build` is active, and
becomes actionable immediately after `build` closes. This directly addresses
the exploratory run where prose gating was interpreted too loosely.

The goal command stores `depends_on` in `goal.created`, supports replacement via
`goal depends <goal> [dependency...]`, rejects unknown/self/cyclic dependencies,
and refuses `progress` or `close` while blockers remain. `brief`, `next`, `tree`,
and parameterized `context` derive current readiness from append-only goal state;
the kernel does not learn goal semantics.

The prompt text itself remains single-source in `PROTOCOL.md`:
`prompt:core` is spliced into every situated turn, while `prompt:growth` appears
only when declarations are pending. `self help` still prints the complete
contract.

The growth layer also sets a discoverability convention for parameterized
views: no arguments should render concise usage and a list of valid keys or
actionable choices. A reader should not need to know an identifier before the
view can teach it. Only malformed or excess arguments should fail.

A real Pi/Luna run is therefore qualitative and exploratory. It may reveal
failure modes or useful behavior, but it must not be reported as an A/B result
for model quality. Future work should repeat across asks, pending capability
shapes, models, and seeds, and score durable outcomes separately from prompt
length.
